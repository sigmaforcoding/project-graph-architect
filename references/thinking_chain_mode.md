# 思考链路模式（Thinking-Chain Mode）

本模式是 skill 的一项专用功能，有两种用途：

| 子模式 | `mode` | 用途 | 一句话 |
|---|---|---|---|
| 复盘 | `review`（默认） | 用户和 AI 一起回看、记住**思考是怎么走到这里的** | 需求 → 问题/方案/验证/发现 → 决定 → 停止点 |
| 规划 | `plan` | 动手前**规划任务路径**，区分不同情况该怎么做 | 目标 → 步骤/判断点（线上写条件）→ 备选/出口 → 目标达成 |

另有两种**写法**，与用途无关，同一份大纲可以各出一张图：

| 写法 | `style` | 读者 | 画布上有什么 |
|---|---|---|---|
| 给人读 | `human`（默认） | 你，以及几个月后不记得对话的你 | 自然语言标题 + 1–3 句摘要；详情是成段的叙述，不出现编号 |
| 给 AI 读 | `ai` | 另一个 AI，当上下文或交接用 | 短标题；详情带节点编号和结构化字段 |

**写法由模型自己判断，不问用户。** 依据请求里的读者信号：

| 信号 | 写法 |
|---|---|
| 默认；用户自己看：复盘、记住思路、给我看、发给同学或同事、放进笔记 | `human` |
| 图是给另一个 AI 的上下文：交给 Codex / GPT / Claude Code、当上下文、写进记忆或 AGENTS.md、压缩一点、省 token | `ai` |
| 两种读者都有：我看完再交给 Codex、自己复盘也让 AI 接手、存档加交接 | `both`，同时写出 `out.prg` 和 `out_ai.prg` |

拿不准时用 `human`：每个 `.prg` 的 README 都嵌着完整大纲 JSON，任何 AI 都能用 `extract` 读回，不会因为选了给人读的版本而丢失信息。
交付时用一句话说明选了哪种写法，用户想要另一种可以直接说。

两种子模式共用同一套**分层树状排版**（`scripts/tree_layout.py`）。
**该排版只在本模式使用**；架构图、流程图、对比图等仍走 SKILL.md 的泳道流程。

---

## 1. 图形语法（两种子模式共同）

- **唯一起点**在顶部：复盘 = 从用户提示词提炼的需求；规划 = 目标。用户原话放 `quote`，进 Details。
- **向下展开**：每往下一层，代表思考推进一步（复盘）或执行推进一步（规划）。分支自然变多。
- **合流**允许：多个分支共同推出一个决定，或多条路径汇到同一步。
- **唯一终点**在底部：复盘 = 停止思考的节点；规划 = 目标达成。
  终点 ≠ 全部解决。未完成 / 未定的分支**停在自己的末端（虚线框）**，不拉长线到终点；
  终点的 Details 自动汇总：当前决定、停止原因 / 完成条件、未完成分支、已排除或出口、下一步。
- **每条边写“为什么走到这里”**（复盘）或“在什么条件下走这条”（规划），≤ 12 个汉字，两行以内。
- 无环。规划中的“重试”画成“重测通过了吗？”这样的新判断点，而不是回边。

## 2. 大纲格式（outline JSON）

```json
{
  "mode": "review",
  "style": "human",
  "title": "图标题",
  "source": "来源说明（哪段对话 / 哪个任务）",
  "overview": "两到四句话讲完整个故事：从哪开始，中间怎么转，现在停在哪。",
  "nodes": [
    {"id": "R", "kind": "requirement", "title": "让 skill 画出真正的思考链路图",
     "short": "让 skill 画出\n真正的思考链路图",
     "summary": "一到三句完整的话，写在画布上。",
     "quote": ["用户原话"], "goal": "...", "constraints": ["..."], "acceptance": ["..."]},
    {"id": "Q1", "kind": "question", "status": "resolved", "title": "上一张图为什么不像思考链路？",
     "short": "旧图为什么\n不像思考链路？", "turn": "2:35 PM，GPT",
     "summary": "要改之前得先弄清楚旧版到底错在哪。",
     "from": [{"id": "R", "why": "先找原因", "short": "先找病因", "by": "reasoning"}],
     "details": ["更长的解释、文件名、命令"], "evidence": ["证据"], "reason": "否定或被取代时必填"},
    {"id": "END", "kind": "stop", "title": "交付 v1.2，等你验收", "summary": "...", "from": [{"id": "D1"}],
     "reason": "为什么停在这里", "decision": ["当前决定"], "next": ["下一步"]}
  ]
}
```

- `title` / `summary` / `why`：给人读写法使用。`short`（节点和连线上都可以有）：给 AI 读写法使用，缺省时退回 `title` / `why`。
- `overview` 和每个节点的 `summary` 在给人读写法下是**必填**，缺了脚本报错；可以改用 `--style ai` 渲染。

- `from` 记录父节点；可以有多个父节点（合流）。只有起点没有 `from`。
- `by`：`reasoning`（推理，灰线）、`user`（用户推动 / 由你决定，蓝线）、`evidence`（证据驱动，青线）。
- `turn`：节点出自对话哪一轮。复盘模式下缺失会警告，因为可追溯是复盘的核心价值。
- 规划模式终点用 `done_when` 写完成条件。

### 节点类型与状态

**复盘 review**

- kind：`requirement` 需求 · `subgoal` 子需求 · `question` 问题 · `option` 方案 · `hypothesis` 假设 · `check` 验证 · `finding` 发现 · `decision` 决定 · `stop` 终点
- status：`adopted` 采用 · `confirmed` 已证实 · `resolved` 已解决 · `rejected` 否定 · `superseded` 被取代 · `pending` 待验证 · `open` 未解决 · `parked` 搁置
- 可作为分支末端：否定、被取代、待验证、未解决、搁置。其余状态必须继续往下连。

**规划 plan**

- kind：`requirement` 目标 · `subgoal` 子目标 · `branch` 判断点 · `step` 步骤 · `check` 检查点 · `decision` 决定 · `stop` 终点
- status（缺省为 `planned`，画布上不显示）：`planned` 计划 · `done` 已完成 · `optional` 可选 · `fallback` 备选 · `unknown` 未定 · `blocked` 受阻 · `abort` 中止 · `handoff` 交给你
- 可作为分支末端：未定、受阻、中止、交给你。
- `branch` 判断点必须 ≥ 2 条出边，每条出边的 `why` 写条件（如“401/403”“超时”“否则”）。超过两种情况时，应有“否则 / 其他”兜底。

## 3. 给人读的写法（human style 的写作规范）

目标：你三个月后不看原对话，只看这张图，也能明白当时发生了什么、为什么这么定。
判断标准：把节点的标题和摘要念出来，听起来像一个人在讲事情，而不是在念笔记。

**标题**：一句完整的短话，说清这个节点的结论或问题，16–28 个字以内。

| 不要 | 要 |
|---|---|
| 41 节点、0 分叉 | 41 个节点，一个分叉都没有 |
| 排版没跟着改 | 排版规则没有跟着改 |
| Model list 只填 Sonnet，覆盖了自动发现 | 模型列表只填了一个，把自动发现盖住了 |
| 副本 entitlement_missing | Claude 副本重签名后丢了 Cowork |

**摘要**（画布上标题下面那段）：一到三句，写清**发生了什么**和**为什么重要**，以句号结尾。
不要只重复标题；能用日常话说的不用术语，非用不可时顺带解释一句。

- 不要：「流水线≠思考，需专用模式。」
- 要：「上一张图按主题分成六条并排的链路。它看起来很满，却表达不出一个问题怎样引出更多问题。」

**连线文字**：一个动作或一个条件，最多 14 个字，例如「你问模型去哪了」「复查旧图」「报 401/403」「否则，其他报错」。
不写「实现缺口」「落地方式」这类只有写的人才懂的词。

**人称**：用户写成「你」，AI 写名字（Claude、GPT、Codex），不用「我」。因为这张图以后会被不同的 AI 和以后的你读。

**符号**：画布上不用 → ≠ / + = 这类记号表达逻辑，用文字说（判断条件里的「401/403」除外）。
文件名、命令、日志关键字放进 `details`，不放标题。

**详情面板**：脚本自动生成成段的叙述（「由「…」引出：…」「这个结论综合了…」「后来引出了…」），
不出现节点编号。终点详情按「停在这里的原因 / 已经定下来的 / 还没解决的 / 放弃了的方向 / 接下来」分段。

脚本会对以下情况给出警告：摘要太短（读不出意思）或太长（画布放不下）、没有以句号结尾、
标题或摘要里有记号符号、连线文字超过两行。

## 4. 从对话提取复盘树（最容易出错的一步）

1. **提炼需求**：从用户提示词提取目标、约束、验收标准。原话放进 `quote`，不要改写成 AI 的话。
2. **按因果，不按主题**：问“这个节点是因为什么才出现的？”，答案就是它的父节点。
   不要把对话按话题分成几条并排的流水线，那是旧模式的失败形态。
3. **标出用户推动的转向**：用户说“继续”“换个中转站”“你觉得呢”“别的无所谓”时，这条边 `by: "user"`，`why` 写用户的意图。
4. **只记录真实发生的探索**。没有讨论过的备选不要补；被否定的方案要写 `reason`。
5. **找停止点**：对话停在哪里、为什么停（等授权、等用户操作、已交付、问题搁置）。
6. **不为凑层数而造节点**。一句话能说清的就放进 Details。

## 5. 规划路径的建模要点

1. 从目标出发，先写主路径的步骤。
2. 每遇到一个**会改变下一步做法的情况**，就放一个判断点；把所有可能结果列成出边。
3. 每条路都要有归宿：到达目标，或走到备选（`fallback`），或停在明确的出口（`handoff` / `abort`），或标记 `unknown`。
4. 不可逆或花钱的步骤，前面应有备份或确认的步骤（例如“先备份配置”“等你授权”）。

## 6. 工作流

```bash
python scripts/thinking_chain.py check outline.json           # 语义检查
python scripts/thinking_chain.py tree  outline.json           # 文字树，给用户确认
python scripts/thinking_chain.py build outline.json out.prg   # 排版 + 松弛 + 写出 + 碰撞自检
python scripts/thinking_chain.py build outline.json out.prg --style ai     # 只出给 AI 读的版本
python scripts/thinking_chain.py build outline.json out.prg --style both   # 同时写出 out.prg 和 out_ai.prg
python scripts/thinking_chain.py extract old.prg outline.json   # 从已有的图取回大纲，接着往下画
python scripts/validate_prg.py out.prg
python scripts/layout_audit.py out.prg
python scripts/preview_prg.py out.prg preview.png             # 可选：交付前自己看一眼
```

- **先出文字树再画图**。用户确认树结构后再 build。
  如果用户已经明确授权直接做（例如说过“继续”“直接画”），可跳过确认，但仍要在交付时附上文字树。
- `build` 返回 3 时仍有残余碰撞：缩短标题或边标签、把长内容移到 Details、拆出子目标，然后重建。
- `build` 会在必要时把合流边的标签移进目标节点 Details（`labels_moved_to_details`），内容不丢。
- **接着画一张已有的图**（例如同一个话题又聊了几轮）：先 `extract` 取回大纲，在原有节点下面接新节点，
  把终点挪到新的停止位置，再 `build`。不要从画布文字反推结构，那样会丢掉 `turn`、`quote` 和状态。

## 7. 语义检查（脚本强制）

错误（不能交付）：
- 起点不唯一、终点不唯一、孤立节点、有环、终点有子节点
- 非末端状态的节点没有往下连（分支既没收束也没标状态）
- 否定 / 被取代 / 中止 / 交给你 节点没写 `reason`
- 节点数 ≥ 6 却没有任何分叉（是流水线，不是树）
- 规划：判断点少于 2 条出边，或出边没写条件
- 给人读写法：缺 `overview`，或有节点缺 `summary`

警告（应处理）：
- 复盘节点缺 `turn`；需求缺 `quote`；终点缺 `reason` / `next` / `done_when`
- 边缺 `why`（终点入边和多父合流除外）；标题或边标签超过两行
- 节点多但层数很少（图太平，检查因果顺序）
- 规划没有判断点（只画了顺利路径）；判断点超过两种情况却没有兜底
- 给人读写法：摘要太短、太长、没以句号结尾、含记号符号；标题或连线用了记号符号

## 8. 视觉约定

- 填色按节点类型：需求/子需求蓝，问题/判断紫，方案/步骤赭，验证/检查青，发现绿，决定灰蓝，终点灰。
- 实线框 = 已确定（采用 / 证实 / 解决 / 计划 / 已完成）；虚线框 = 未定或末端（待验证 / 未解决 / 搁置 / 否定 / 被取代 / 可选 / 备选 / 未定 / 受阻 / 中止 / 交给你）。
- 线色：灰 = 推理；蓝 = 用户推动；青 = 证据驱动；橙虚线 = 走向被排除 / 备选 / 出口；绿 = 收束到终点。
- 起点和终点字号大一级。图例放在树的活动空间之外（右上）。
